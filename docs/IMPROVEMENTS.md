## Rules that apply to every task

Read this section first. Breaking one of these rules is worse than not finishing a task.

### Setup
```
git clone -b src https://github.com/atxr1/Mike-Arena mike-arena && cd mike-arena
bun tools/build.mjs --all          # fetches sources, builds every asset into site/
cd site && python3 -m http.server 8078 &
```
Open `http://localhost:8078/`. After every source change run `bun tools/build.mjs` again (no `--all` needed) and reload.
`docs/STATUS.md` explains where everything is. `docs/DECISIONS.md` explains why things are the way they are.

### Never do these
- **Never change the `atxr1/Polish.-` repository.** It holds the original Arena and the owner wants it frozen.
- **Never change what an existing match does unless the task says so.** The simulation in `src/game/` and
  `src/modes/match.js` is deterministic: the same seed and inputs must always give the same match. Play of the Match
  depends on it. Inside those files never use `Math.random()`, `Date.now()`, `performance.now()` or anything read
  from the screen. Use the sim's own seeded random generator (search for `mulberry32`).
- **Never let the cinematic director (`src/ui/cinema.js`) change the simulation.** It only decides how things are shown.
- **Never draw new in-world art with canvas arcs, gradients or rounded shapes.** Everything inside the arena is pixel
  art; `bun tools/shapelint.mjs` fails the build of anything else. Menus and overlays are HTML/CSS and are exempt.
- **Never rename the save namespace (`mikearena.`) or remove a save field.** Only add fields (see "Saves" below).
- **Never add a library, a framework or a network request.** The game is plain JavaScript and works offline.
- **Never edit `docs/CONTENT.md` by hand.** It is generated by `bun tools/gen_docs.mjs`.

### Style of the code and the text
- Match the surrounding code: ES modules, semicolons, template-string HTML in `src/ui/screens.js`,
  CSS in `src/ui/styles.css`.
- Every new button in a menu needs the class `nav` (that is what makes it reachable by controller and keyboard), and
  every new screen needs a `back` function in its `setScreen` options. Copy an existing screen such as `credits()`.
- Text the player reads is sentence case, short, and describes what happens: "Next opponent", not "Continue".
- New animation must be switched off when `settings.reducedMotion` is on. For CSS, add the override in the
  reduced-motion block at the end of `styles.css`.
- The game is played on an iPhone in landscape. Check every new screen at 844×390; nothing may scroll sideways or
  sit under the notch (existing screens use the safe-area padding of `.screen` — keep new content inside `.screen`).

### Saves
Saves are in `src/saves/store.js`.
- Adding a field to `records` or `last`: add it to `DEFAULTS` with its starting value. Old saves pick up the default
  automatically when read. No migration is needed.
- Adding a field to `settings`: add it to `DEFAULTS.settings`, raise `v` there and in `SCHEMA.settings` by one, and add
  a migration entry for the old version in `MIGRATE.settings` that copies the pattern of the existing entry.
- Adding a whole new saved object (task 6): add a key to `SCHEMA`, `DEFAULTS` (use `null` for "nothing saved", as
  `tournament` does) and `MIGRATE`.

### Checks before every commit
Run all of these. All must pass.
```
bun tools/build.mjs
bun tools/validate.mjs
bun tools/replaycheck.mjs        # must say every match replays identically
bun tools/shapelint.mjs          # must say 0 violations
PORT=8078 node tests/e2e.mjs     # with the local server running
```
Then take a screenshot of anything you added at 844×390 and look at it. `tests/menus.mjs` shows how to drive the menus
with Playwright and save screenshots; copy it for new screens. `window.__app` is the running app when the URL has
`?test=1`.

If `replaycheck` fails after a task marked "No" in the table above, you changed the simulation by accident: undo it.

### Finishing a task
1. Add a line to the top entry of `docs/CHANGELOG.md` (start a new entry `Mike Arena 1.1.0` for the first task you
   ship, and reuse it for the rest).
2. Set the same version in `src/version.js` and `package.json`.
3. Add an e2e check for the new feature to `tests/e2e.mjs` (one or two assertions is enough).
4. Commit with a message that says what the player gets.
5. When all the tasks you are doing are finished, update "Last verification" in `docs/STATUS.md`, then publish:
   `bun tools/build.mjs --zip`, copy the contents of `site/` to the root of the `main` branch (keep `.nojekyll` and
   the `README.md` that is there), push, and push the source to `src`.

### When to stop and ask the owner
- A check fails and you cannot find why within a few attempts.
- A task needs new artwork or sound.
- You think a rule above has to be broken.
Report what you tried. Do not guess, and do not delete a failing test.

## Task 1 — Records screen

**Why.** The game already saves wins and losses for every Pokémon (`records.byFighter`), but only shows three numbers
in the footer of the main menu.

**What the player gets.** A "Records" item in the main menu that opens a screen with their totals and a table of every
Pokémon they have used.

**Steps.**
1. In `src/ui/screens.js`, in `main()`, add a button after "Tournament":
   `<button class="mm-item nav" data-go="records">Records<small>Your wins with every Pokémon</small></button>` and handle
   `g === 'records'` in the click handler by calling `this.records(() => this.main())`.
2. Add a method `records(back)` modelled on `credits(back)`. Read `this.store.read('records')`. Show:
   - a row of totals: battles played, wins, losses, draws, championships, win rate as a whole percentage (show "—"
     when nothing has been played);
   - a table sorted by wins, highest first: Pokémon name (`CONTENT.species[id].name`), wins, losses, win rate.
     Skip ids that are no longer in `CONTENT.species`.
   - when `byFighter` is empty, one line instead of the table: "Win a battle to start your records."
3. Reuse the table styling of the results screen (search `styles.css` for the results table rules) so it matches.
4. The list can be longer than the screen: make only the table area scroll vertically (`overflow-y:auto`), not the page.

**Done when.** The screen opens from the main menu by touch, controller and keyboard; Back returns to the main menu;
after winning one battle the Pokémon appears with 1 win; a fresh save shows the empty line.

## Task 2 — Move list in the pause menu

**Why.** During a battle there is no way to check what the four moves do. That information is only on the fighter
select screen.

**What the player gets.** A "Moves" button in the pause menu showing the active Pokémon's four moves, its Ultimate and
what R does.

**Steps.**
1. In `src/ui/screens.js`, `detailHtml(id, vsId, opponent)` already builds this information for the select screen.
   Read it to see which fields it uses for move name, type, stamina cost and cooldown, and where the R text comes from
   (`TRAV_TEXT` at the bottom of the file).
2. In `menu(kind, o)` add `<button class="menu-btn nav" data-a="moves">Moves</button>` after "Controls". Do it the
   same way the "Rules" button works: on click, replace `panel.innerHTML` with the move list and a Back button that
   restores the pause menu.
3. The pause menu needs to know the active Pokémon. Where `battle.js` opens the menu (search for `.menu(`), pass the
   id of the player's active fighter in the options object, for example `fighterId`. If it is missing, do not show the
   button.
4. Show for each move: the button glyph (use `face('cross', 18)` and so on, in the order ✕ □ △ ○), name, type,
   stamina cost, cooldown if it has one. Then the Ultimate name, then one line for R.
5. In a Trainer Battle the active Pokémon changes: read the id at the moment the menu opens, not when the battle starts.

**Done when.** Pausing and choosing Moves shows the correct four moves for the Pokémon on the field; Back returns to
the pause menu; Resume still works afterwards; the panel fits at 844×390 without scrolling.

## Task 3 — Cinematics setting

**Why.** The camera work and freeze-frames are the point of this edition, but some players will want less of it and
the only control today is "Reduce motion and flashes".

**What the player gets.** A three-way setting, "Cinematics": Full, Light or Off.
- **Full** — as now.
- **Light** — what "Reduce motion and flashes" does to battles today: shorter freezes, no inverted flash frames,
  gentler camera kicks.
- **Off** — no camera zooms, freezes, black bars, cut-ins or stamps. The VS card and the K.O. still happen.

**Steps.**
1. Add `cinematics: 'full'` to `DEFAULTS.settings` in `src/saves/store.js` and follow the settings rule under "Saves".
2. In `settings(back)` in `screens.js`, add a three-button row copied from the "Touch button size" row, with values
   `'full'`, `'light'`, `'off'`.
3. In `src/modes/battle.js` the director is created with `new Director(app, { reduced })`. Change it so that
   `reduced` is true when `settings.reducedMotion` is on **or** `settings.cinematics === 'light'`.
4. For Off: the director already has a switch, `dir.off` (the capture lab in `src/dev/lab.js` uses it). After creating
   the director, set `dir.off = true` when `settings.cinematics === 'off'`. Do the same for the second director that
   Play of the Match creates (search `battle.js` for `potmDir`).
5. Today `off` only stops the drawing: `render()` in `battle.js` skips the camera, black bars, flash and overlays when
   `D.off` is true. Three things still happen and must also be switched off:
   - **Freezes.** `frame()` in `battle.js` stops stepping the simulation while `dir.hold > 0`. Treat the hold as 0
     when `dir.off` is true.
   - **The establishing shot.** After the VS card the battle enters the state `'establish'` and waits for
     `dir.introDone`. When `dir.off` is true, call `finishEstablish()` straight away instead.
   - **Hidden touch controls.** `touch.cine(...)` hides the controls during holds and before "Fight!". With Off, hide
     them only once the match is decided.
6. Play a full match on Off and confirm the touch controls are visible and working from the first moment the fighters
   can move, and that the "Fight!" sound and the K.O. still happen.
7. "Reduce motion and flashes" keeps working exactly as before and still calms the menus.

**Done when.** Each of the three values visibly changes a battle as described; a match can be started, paused and
finished on each; the choice survives a reload.

## Task 4 — "Next opponent" on the results screen

**Why.** After a Quick Battle the only choices are Rematch (same opponent), Change setup and Main menu. Playing a
string of different opponents takes many taps.

**What the player gets.** A "Next opponent" button after a Quick Battle that starts a new battle straight away with
the same Pokémon or trainer, the same difficulty, a random new opponent and a random map from the same environment.

**Steps.**
1. In `results(info, setup, ctx)` in `screens.js`, find where the Rematch button is built and what it calls.
2. Add the button only for Quick Battles (not tournament matches, and not the ladder from task 6).
3. On click, copy the setup, set `opponent: 'random'` and `map: 'random'`, and launch it the way "Fight again" on the
   main menu does (`launchQuick`). A random pick can land on the opponent just fought: pick again until it is a
   different one.
4. Button order: Rematch, Next opponent, Change setup, Main menu. Rematch stays the default-focused button.

**Done when.** The button appears after a Quick Battle and not after a tournament match; pressing it starts a battle
against a different opponent with the player's side unchanged.

## Task 5 — Training mode

**Why.** There is nowhere to learn a Pokémon's moves without an opponent hitting back and a clock running.

**What the player gets.** A "Training" item in the main menu. They pick an environment, a Pokémon, an opponent and a
map, then fight with no time limit against an opponent that does not attack. Both sides' HP refills a few seconds
after they stop taking damage. Nothing is saved to their records. A pause-menu option switches the opponent between
"Stands still" and "Fights back".

**This task changes the simulation. Follow these rules exactly.**
- Every new behaviour is behind one new option, `training`, passed in the match options. When the option is absent or
  false, the code must run exactly as before. `replaycheck` proves this: it must still pass with identical results.
- No randomness and no clock reads (see "Never do these").

**Steps.**
1. Read how a match is created: `src/modes/match.js` (options, `sides`, `control: 'cpu'`, `level`) and the top of
   `src/game/sim.js` (constructor options, the `MATCH` constants, the timer).
2. Add `training` to the sim options. When it is true:
   - the match clock does not count down and time can never end the match;
   - a fighter that reaches 0 HP is set back to full HP instead of fainting (so the match never ends);
   - each fighter regains HP steadily once 3 seconds (180 ticks) have passed since it last took damage.
3. The opponent that stands still: in `src/game/ai.js`, add a level named `dummy` to `LEVELS` by copying `easy`, and
   make the AI's decision function return "no input" straight away when `this.level === 'dummy'`. Do not add `dummy`
   to the difficulty screen: `levelStep` lists every key of `LEVELS`, so filter it out there.
4. Menu: add "Training" to `main()` after "Quick Battle". Reuse the Quick Battle steps (environment, Pokémon,
   opponent, map) with `mode: 'training'`, Pokémon Battle format only, and skip the difficulty step.
5. In `battle.js`, for training matches: hide the timer in the HUD, do not show the results screen (Quit in the pause
   menu returns to the main menu), do not record a Play of the Match, and do not write to `records`.
6. Pause menu: add an "Opponent: stands still / fights back" button for training matches. Changing it restarts the
   training match with the opponent on `dummy` or `normal`.
7. Add training to the capture test or write a short Playwright script: start training, attack the dummy until its HP
   reaches 0, confirm the match continues and its HP comes back.

**Done when.** All checks pass, `replaycheck` results are unchanged, a training session can run for five minutes
without ending, HP refills as described, and wins and losses in Records do not change.

## Task 6 — Arcade ladder mode

**Why.** Quick Battle is one fight and Tournament is a bracket. There is no simple "how far can I get" mode.

**What the player gets.** "Arcade" in the main menu: pick an environment and one Pokémon, then fight six opponents in
a row. Opponents 1–2 are on Easy, 3–4 on Normal, 5–6 on Hard; the last is always a Legendary from that environment if
the roster has one. HP is restored between fights. One loss ends the run. Their best run per environment is saved and
shown on the Records screen.

**Steps.**
1. Read `src/modes/tournament.js` and the tournament methods in `screens.js` (`launchTour`, `bracket`,
   `playTourMatch`, `recordTour`, `afterTourMatch`). Arcade is the same idea with a list instead of a bracket; copy
   the flow, do not modify the tournament code.
2. Save: add an `arcade` object following "Saves" (`null` when no run is active). It holds the environment, the
   player's Pokémon, the six opponents, the six maps, the index of the next fight and the run's seed. Save it
   **before** each fight starts and again as soon as a result is known, the way the tournament does, so closing the
   app mid-run loses nothing.
3. Choosing opponents: pick six different Pokémon from the environment's roster, excluding the player's own, using a
   seeded generator created from the run's seed (`mulberry32` in `src/core/util.js`) so a resumed run has the same
   opponents. Maps: cycle through that environment's maps.
4. Between fights show a simple ladder screen: six rungs with the opponents' names and difficulty, the beaten ones
   marked, the next one highlighted, and a "Fight" button. Model it on `bracket()`.
5. Main menu: show "Resume arcade run" when a run is active, as "Resume tournament" does.
6. After the sixth win show a completion screen modelled on `championship(T)`.
7. Records: add `arcadeBest: {}` to `DEFAULTS.records` (environment → highest number of wins in one run, 0–6) and
   show it on the Records screen from task 1.
8. The results screen after an arcade fight shows "Continue" (to the ladder) on a win and "Main menu" on a loss. No
   Rematch.

**Done when.** A run can be played start to finish, closed and resumed in the middle, lost, and completed; best runs
appear in Records; the tournament still works exactly as before.

## Task 7 — Even out trainer team strength

**Why.** Each Pokémon is balanced one against one, but whole trainer teams are not. In Trainer Battles between CPUs,
team win rates run from about 20 % to 87 % (Nurse Joy's air team is the strongest, Paul's the weakest). This is the
one balance problem listed in `docs/STATUS.md`.

**What the player gets.** Trainer Battles that are close to fair whichever trainer they pick.

**This task changes balance data. It is slow and mechanical: measure, adjust, measure again.**

**Steps.**
1. Measure first. Run `bun tools/harness.mjs --runs 600 --format trainer` and save the per-team win rates for each
   environment. (Read the top of `tools/harness.mjs` for its options.)
2. Add a table of per-team multipliers. In `src/content/balance.js` add a second export:
   `export const TEAM_BALANCE = { 'air:nurse_joy': { hp: 0.92 }, ... };` — key is `environment:trainer`, missing
   entries mean 1.
3. Apply it. The per-fighter table is applied in `src/game/fighter.js` (search for `BALANCE`). In the same place, when
   the match format is trainer and the side has a trainer id, also multiply that side's fighters' maximum HP by the
   team's `hp` value. Pokémon Battles must not be affected: confirm with `replaycheck`, which must give the same
   results for Pokémon-format matches as before.
4. Tune. Keep every multiplier between **0.88 and 1.12** so no team feels obviously padded. For a team that wins more
   than 58 %, lower its value by 0.03; for one that wins less than 42 %, raise it by 0.03. Re-run the harness. Repeat
   until every team is between 40 % and 60 % or its multiplier has reached the limit.
5. If a team is still outside 40–60 % at the limit, swap one Pokémon in that team's entry in
   `src/content/trainers.js` for another from the same environment's roster that suits the trainer, and say why in
   `docs/DECISIONS.md`. Change as few teams as possible.
6. Run `bun tools/gen_docs.mjs`, then replace the "Trainer team strength varies" item in `docs/STATUS.md` with the
   new measured range.

**Done when.** The harness shows every trainer team between 40 % and 60 % in every environment over 600 matches, with
0 errors and 0 stalls; Pokémon Battle results are unchanged; all checks pass.

## Things not to attempt

These look like obvious improvements but cannot be done well without the owner, new artwork or a real device:

- **Missing Mega Evolutions** (Venusaur, Blastoise, Gyarados, Scizor, Sceptile, Blaziken, Salamence, Metagross,
  Garchomp). They need sprite sheets that do not exist in the sprite source. Do not draw them.
- **Serpent bodies** (Gyarados, Rayquaza, Milotic and the others). They were tuned by eye over many rounds; leave them.
- **Vibration.** Safari on the iPhone does not support it. The existing call is harmless and does nothing there.
- **Online or two-player battles.** A much larger project than anything in this list.
- **Sound mixing.** The automated browser is silent, so sound changes cannot be checked without the owner's phone.
- **Changing moves, stats or the per-Pokémon balance table.** They were tuned over thousands of simulated matches.
